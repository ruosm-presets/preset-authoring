# add-brand-preset

Веди процесс от имени бренда до готового закоммиченного `<item>` в локальном
клоне [literan-moscow](https://github.com/ruosm-presets/literan-moscow)
(файл `russian_shops.xml`). Два режима: добавление нового пункта (6 шагов
ниже) и обновление существующего (раздел «Режим обновления»).

## Вход-опросник (карточка бренда)

Заполняй карточку бренда как визит: **по одному пункту за вопрос**, в
порядке полей формы (форма — в [references/item-template.md](references/item-template.md)).

1. Обход формы сверху вниз: name → website → город → тип → … Каждое поле —
   отдельный вопрос. Спросил — остановись, дождись ответа, только потом
   следующее.
2. Ответ «не знаю» / «—» / «дальше» — поле остаётся пробелом, его закроет
   авто-исследование (шаг 1 ниже). Пропущенное не переспрашивай.
3. Если пользователь назвал несколько фактов одним сообщением — прими их
   как ответы на соответствующие поля и не спрашивай эти поля повторно;
   продолжай опрос со следующего незаполненного.
4. После обхода формы: авто-исследование закрывает пробелы (адресная
   страница из навигации сайта, соцсети и email из футера, wikidata
   поиском по названию) → покажи заполненную карточку целиком → получи
   подтверждение → вставляй пункт.

## Процесс добавления (6 шагов)

### 1. Исследование бренда

Собери факты из первоисточников:

- Wikidata API: лейбл ru/en, `P856` (сайт), `P576` (дата закрытия),
  поисковые синонимы.
- Сайт бренда: найди страницу адресов — обычно в навигации
  «Магазины/Адреса/Карта».
- Соцсети: vk/ok/telegram из футера сайта.

Проверяй гипотезы через curl с браузерным User-Agent; помни про гео/бот-блоки
(`401`/`403`/`498` ≠ мёртвый сайт). Если сеть закрылась или ребренднулась —
остановись и доложи человеку.

Читать: [references/update-playbook.md](references/update-playbook.md)
(разделы 1–2: матрица триажа ссылок и методика проверки Wikidata — годятся
и для новых брендов, не только для обновлений) — когда проверяешь живость
сайта и QID бренда.

### 2. Данные пункта

Заполни шаблон `<item>`: amenity/shop/cuisine, brand, name + ru.name
(латиница/кириллица по правилам), контакты (только проверенные факты —
никаких выдуманных телефонов), wikidata если объект существует, часы работы
как values-комбо из шаблонов чанков.

Читать: [references/item-template.md](references/item-template.md) (скелет
`<item>` с плейсхолдерами и примеры «хорошо/плохо») — прямо перед сборкой
пункта.

### 3. Иконка

Сначала реюз существующего файла из `pics/icons/` (подбор по смыслу, список —
`ls pics/icons/`); если подходящего нет — Twemoji по кодопоинту, имя
snake_case, файл в `pics/icons/`, URL Pages
(`https://ruosm-presets.github.io/literan-moscow/pics/icons/<file>`).

Читать: [references/icon-pipeline.md](references/icon-pipeline.md) (конвейер
реюз → Twemoji → имя → URL; формат имён проверяет чекер) — на шаге подбора
иконки.

### 4. Вставка

Найди группу; определи позицию по сортировке (числа → латиница → кириллица,
внутри — алфавит; при наличии ru.name сортировка по нему). Собери `<item>`
по шаблону; порядок атрибутов: key/ref → text/name → ru.text/ru.name →
values → ru.display_values → default → type → preset_name_label →
name_context → icon (последний). Максимум переиспользования чанков; порядок
полей экранной формы — как во встроенных заготовках JOSM.

Читать: [references/conventions.md](references/conventions.md) (порядок
полей, сортировка, атрибуты, комментарии/отступы/пробелы, язык, чанки) —
перед любой правкой XML.

### 5. Верификация

В клоне literan-moscow:

```bash
python3 scripts/check_presets.py --no-http russian_shops.xml
```

Ожидай 0 ошибок; дополнительно `xmllint --schema` при наличии xmllint.
Каждое падение чекера исправь до коммита.

### 6. Коммит

Коммить только по явному слову пользователя. Сообщение — одна строка, стиль
репозитория (см. `git log`). Версию пресета не трогай — инкрементит CI.

## Режим обновления (update)

Триггеры: CI-ворнинг по ссылке пункта, ребрендинг сети, изменившиеся
контакты/часы/иконка, просьба пользователя «обнови пункт X».

1. Найди пункт: группа + name (уникальность внутри группы гарантирована
   чекером); прочитай текущие теги целиком.
2. Исследуй как в шаге 1 основного процесса.
3. Минимальный диф: меняй только подтверждённые факты (ссылка, бренд,
   контакты, иконка); стиль и сортировку не трогай, если они не сломаны.
   Ребрендинг = переименование пункта + brand + ссылка (+ иконка при
   необходимости), с удалением устаревшего brand:wikidata, если у нового
   бренда нет QID.
4. Верификация и коммит — шаги 5–6 основного процесса.

Читать: [references/update-playbook.md](references/update-playbook.md)
(триаж «мёртвый» vs «бот-блок» vs «переезд», сценарии ребрендинга и
закрытия, правило минимального диффа) — целиком, при любом входе в режим
обновления.

Удаление пунктов (сеть закрылась) — всегда эскалация к человеку, агент сам
не удаляет.

## Guardrails (жёсткие правила)

- PII в пресет, тесты и коммиты не попадает никогда.
- Мёртвый/сомнительный бренд → вопрос человеку, пункт не удалять самому.
- Не выдумывать данные (телефоны, wikidata, часы) — только из источников.
- Скилл не модифицирует CI, чанк-инфраструктуру и чужие пункты без запроса.
- Изменения только в клоне literan-moscow; push — только по слову.
